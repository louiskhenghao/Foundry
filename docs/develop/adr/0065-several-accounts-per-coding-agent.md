# ADR-0065: Several accounts per coding agent, and switching when a usage limit stops a session

**Status:** accepted · 2026-10-22 · amends [ADR-0017](0017-goal-provider-and-account-isolation.md) (independent accounts) and [ADR-0001](0001-drive-host-claude-cli-not-agent-sdk.md) (the host login)

## Context

A subscription's usage limit (Claude's five-hour and weekly windows, ChatGPT's for Codex) stops long goals halfway, and Foundry then waits for the reset: new sessions pause, and before this change the session the limit cut was judged like a finished one, its half-done work reviewed, its attempt counted against the task's retries. A person with more than one subscription of their own (a personal and a work account, say) wants Foundry to hold them all, to choose which one sessions run on, and, if they say so, to go on with the next one when the current one is used up, the cut session carrying on where it stopped.

The coding agents keep a sign-in per config dir: Claude Code per `CLAUDE_CONFIG_DIR` (on macOS the Keychain item is keyed by it; the documented way to keep a work and a personal account apart), Codex per `CODEX_HOME` (its keyring entry is keyed by a hash of the path). The Antigravity CLI has no such variable, and on macOS every agy sign-in shares one Keychain item. A session's transcript lives in the config dir, so a session started on one account is only resumable on another that can see it. Whether the API accepts a resumed conversation from another account (Claude's thinking signatures, Codex's encrypted reasoning) is not documented.

The terms matter, and Foundry is public. Anthropic writes that "advertised usage limits for Pro and Max plans assume ordinary, individual usage" and reserves enforcement "without prior notice"; OpenAI's Terms of Use forbid using the services to "circumvent any rate limits or restrictions"; a Google staff answer called switching between paid accounts one owns acceptable. Going on past a limit with another account can be read as against the first two.

## Decision

**Accounts.** Claude Code and Codex hold several subscription sign-ins each; Antigravity keeps one. Account 1 is the machine's own sign-in, `native`: the coding agent's default home, never pointed at with `CLAUDE_CONFIG_DIR` (setting it, even to `~/.claude`, makes Claude Code look for a Keychain item it does not have). Every other account lives in a home Foundry makes, `<data>/accounts/<agent>/<id>/`, where only the credentials are its own: everything else is a link to the native home (Claude: `skills`, `plugins`, `agents`, `commands`, `output-styles`, `hooks`, `plans`, `settings.json`, `CLAUDE.md`, and `projects` and `sessions`, which are created in the native home when missing; Codex: `skills`, `plugins`, `prompts`, `rules`, `hooks`, `config.toml`, `hooks.json`, `AGENTS.md`, `sessions`). So a skill or plugin installed once reaches every account, and a transcript written on one account is where every other one looks. A missing link is made before each session; an entry the account has of its own (a file the coding agent wrote there itself) stays. Claude Code's user-scope MCP servers live in the native `.claude.json`, which an added home has its own of, so a session on an added account is handed them with `--mcp-config`. A token in the environment (`CLAUDE_CODE_OAUTH_TOKEN`, the Docker route of `claude setup-token`) takes precedence over the credentials in any config dir, so it is the native sign-in's alone: a session, status read or sign-in on an added account runs without it. Signing in runs the coding agent's own flow in the new home (`claude auth login`, `codex login --device-auth`), the same one the Accounts page already drives; only a sign-in that ends signed in, as a person and organisation not added yet, becomes an account (`account.added`), and anything else deletes the home. Removing an account signs it out and deletes its home (links, never what they point at, and nothing outside the accounts folder). The accounts are events (`account.added`, `account.removed`, `account.reordered`, `account.switched`) projected into `accounts` and `current_accounts`.

**The current account.** Each coding agent has one current account, and every new session of it runs there: the engine's runner wrapper hands the session the account's home (`RunSpec.configHome`) and books the session under it (`session.usage.accountId`). Use now makes another account current; sessions already running finish on theirs. Adding an account or switching is allowed while work runs; signing out the native sign-in still is not (its credentials are the local CLI's).

**A usage limit.** A session stopped by its account's limit (a rejected `rate_limit_event`, or a limit's error text: Claude Code's "You've hit your … limit", Codex's "You’ve hit your usage limit", "out of credits", "spend cap", Antigravity's `RESOURCE_EXHAUSTED … Individual quota reached`) marks that account limited until its reset (`account.limited`; the event's reset, a "Resets in 2h39m" in the text, Codex's quota windows, or five minutes). A provider being overloaded is not an account's limit. Then:

- *Auto switch on* (Settings `accounts.autoSwitchClaude` / `autoSwitchCodex`, off by default; turning it on on the Accounts page quotes the provider's terms and asks the person to confirm the accounts are theirs): the next account in the list that is not limited becomes current (`account.switched`, `auto: true`), and nothing pauses. It stays current after the old one resets; there is no switching back. With every account limited, new sessions pause until the first of them resets, and the pause's end moves them to it.
- *Off*: new sessions of the coding agent pause until the current account's limit resets, as before. The pause offers Switch and continue (the usage banner, and a Telegram or Discord button) when another account is not limited: it makes that account current and lifts the pause.
- A limit that hit an account sessions have already left changes nothing while the current one is fine.

Work never moves to another coding agent.

**The cut session carries on.** A worker session a usage limit stopped is not reviewed or judged done half-way. Its attempt waits as interrupted while sessions are paused and resumes its own session (continuation reason `usage_limit`) once they run again, on whichever account is current then and after a restart too; such a resume does not count towards the continuation cap, and a limit that stopped a session before it began gives its attempt back. If the coding agent refuses the resume (the conversation is not where it looks, or the API rejects its earlier turns, as it may for another account's), a new session takes over the attempt in the same workspace with the task's full prompt and a handoff: what the earlier session committed, what the task changed so far, what it said last.

## Consequences

Cross-account resume is untested on real accounts: no second Claude or ChatGPT subscription was at hand when this was built. The handoff is what makes it safe either way; a resumed conversation also starts on the new account without a prompt cache, so its first turn reads the whole context again. The refusals recognised are Claude Code's "No conversation found", a thinking block's invalid signature, and Codex's missing session or unverifiable encrypted content; another wording fails the attempt as before.

Only worker attempts carry on this way. Other sessions a limit stops (Clarify, the reviewers, a merge attempt, the documenter) fail as they did and run again on their own paths, on the account current by then.

An added Claude home writes its own `.claude.json` (its sign-in, project state). Claude Code may also replace a linked `settings.json` with a file of its own if a session there changes settings; the account then keeps its own copy, which Foundry leaves alone. A Codex home keeps its own state database; resuming a thread from another account relies on the CLI finding the rollout file under the shared `sessions/`.

The Accounts page lists each coding agent's accounts with the current one, its plan and, while it holds, the limit's reset. The per-window rate-limit table and the Usage page still describe the provider as a whole.

On Docker the homes sit in the data volume, so a backup of it holds the added accounts' credential files (Claude Code's `.credentials.json` on Linux, Codex's `auth.json`), readable by their owner only.
